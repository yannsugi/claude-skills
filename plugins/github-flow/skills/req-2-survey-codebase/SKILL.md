# req-2-survey-codebase

要件レイヤの2番目。L 判定の Issue に対する網羅的調査。最大分割の前提条件。
思想は `${CLAUDE_PLUGIN_ROOT}/DESIGN.md` の「要件レイヤの規律」(トリアージ L の項)と「通底する原則」(system-map)。

**核**: 網羅の定義を先に固定し、自己申告を検証可能にする。産物は「各完了基準に既存で応えられるか」の表と影響マップであって、原因の推理ではない。

## 入力契約

`${CLAUDE_PLUGIN_ROOT}/references/principles.md` に従う(出力先・書式・技術事実の断定・マスタの扱い)。

読んでよいもの: 対象 Issue 本文とトリアージ結果(完了基準 C1〜Cn を含む)、system-map(あれば起点にする)、コードベース全域。
読んではいけないもの: 他 Issue の実現案・PR。Issue 本文にある原因の推測(読んでも、それを追う調査にしない)。

## 手順

1. **マトリクスを先に作る** 領域(FE / BE / IaC / データ)× 観点(参照 / 変更 / 暗黙の依存)の12セル。調査を始める前に全セルを「未着手」で置く。repo に無い領域も行を消さず「確認済み(該当なし)」で埋める(無いことも網羅の一部)
   - 参照: この Issue の入口・データを読んでいる場所
   - 変更: 書き換えている場所
   - 暗黙の依存: 設定・環境変数・スケジュール・命名規約・ドキュメントの手順など、コードの参照関係に現れない結びつき
2. **起点を決める** system-map があれば該当項目から差分確認(全量探索は初回のみ)。無ければ初回として全量探索
3. **領域ごとに探索する** 該当領域が2つ以上あり、かつ領域ごとにディレクトリが分かれている(目安: 合計200ファイル超)なら、領域ごとにサブエージェントを並列に出して集約する。各エージェントには担当領域の3セルと完了基準の一覧を渡し、ゲート・フラグ・権限に関する発見は「ファイルパス:行+原文の抜粋」で返させる。集約時にその原文を落とさない。小さければ単独で全量を読む
4. **セルを消し込む** 各セルを次のいずれかにする。「確認済み」には何を見て確認したかを必ず添える(ファイルパスまたは検索語)
   - 確認済み(該当あり): 見た場所と、該当箇所の一覧
   - 確認済み(該当なし): 見た場所
   - 未確認: 理由(アクセスできない・時間切れ・判断不能)
5. **完了基準ごとに答える** 各 C について3問に答える。「既存で満たせる」と答えるときは、その機能の入口と根拠行を添える。マスタ・seed を根拠にするなら正の所在が未確認であることを書く
6. **前例を挙げる** Issue が求める新規成果物の種類(画面・バッチ・API・マスタ追加など)ごとに、repo 内の直近の前例を1件挙げる(場所と、その前例が触っているファイル群)。前例が無ければ「なし」と書く
7. **影響マップを書く** 該当ありのセルから、影響箇所を「場所 / 何が影響するか / つながり」で列挙。つながりは Issue の入口・データとその場所の関係: 直接(その入口・データを扱っている)/ 経由(間接に扱う)/ 関係しうる。原因である可能性の高さではない。同じ事実が複数箇所に定義されている(二重管理)箇所は明示する
8. **未確認セルを⚠候補として渡す** req-3 が⚠に浮上させ、承認時に人間の目に入るようにする
9. **system-map を更新する** 書くのは場所・関係・鮮度だけ。要約や調査結果の転記はしない。出力先は principles.md の規則どおり(repo への書き込みは明示指示があるときだけ)
10. **出力** 下の書式で成果物を提示する

試走でローカルファイル `<name>.md` を対象にする場合は、作業用ディレクトリの `<name>.survey.md` に書く。

## system-map の書式

```
# system-map
<!-- 索引であって本文ではない。要約を書かない。鮮度が古い項目は「未確認」に降格する -->
| 項目 | 場所 | 関係 | 最終確認 (Issue / 日付) | 状態 |
|---|---|---|---|---|
| ベンダー権限定義 | scripts/create-vendors.sh, README.md#M2 | 二重管理 | #12 / 2026-09-14 | 確認済み |
```

## 出力書式

```
## 網羅的調査

### 完了基準ごとの答え
| C | 完了基準 | 既存で満たせるか | 新規の仕組みが要るか | repo 外への依存 | 根拠(パス:行) |
|---|---|---|---|---|---|
| C1 | … | 満たせる(入口: …) | 不要 | なし | … |
| C2 | … | 満たせない | 要る(…) | 外部 API X | … |

### 前例
| 新規成果物の種類 | 直近の前例 | 触っているファイル群 |
|---|---|---|

### マトリクス
| 領域 \ 観点 | 参照 | 変更 | 暗黙の依存 |
|---|---|---|---|
| FE | 該当なし(src/ に UI 無し) | … | … |

### 影響マップ
| 場所 | 何が影響するか | つながり | 根拠(ゲート・フラグ・権限は原文を残す) |
|---|---|---|---|

### 未確認(⚠候補)
- …
```

## よくある失敗

- マトリクスを最後に埋める → 網羅の定義が後付けになる。先に12セル置く
- 「H1 最有力仮説」「切り分け順」「次の一手」を書く → 原因の推理は実現案の仕事。影響の場所だけ書く
- 「全ファイル読んだ」と書いてセルが無い → 自己申告。セルごとに見た場所を残す
- 影響マップだけ出して、完了基準ごとの答えが無い → 60行の表は読まれない。上層の C 表を先に置く
- 集約の要約で「設定フラグの内側」と断定し、根拠行が無い → 原文の抜粋が無い主張は⚠に落とす
- system-map に調査結果の要約を書く → 索引。場所と関係と鮮度のみ
- 出力にローカルの絶対パスを書く → repo 相対パス
