# design-1-propose-with-diagram

設計レイヤの1番目。承認済みの受け入れ基準に対して「進み方」を提示し、人間が仮説として採択できる形にする。
思想は `${CLAUDE_PLUGIN_ROOT}/DESIGN.md` の「実現案の提示仕様」節。実現案は違和感の検出器として設計する。

**核**: 目次表(T ごとの対応可否)だけで「どこに実装が要るか」が分かること。人間向けの本文と AI 向けの実装メモを混ぜない。却下案と⚠を自分で名指しする。

## 入力契約

`${CLAUDE_PLUGIN_ROOT}/references/principles.md` に従う(出力先・書式・技術事実の断定・分割の条件)。

読んでよいもの(全列挙):
- 対象 Issue の「## 実装前の要件・受け入れ基準の整理」節(承認済み)と「## コンテキスト」節(調査結果・技術判断の根拠)
- system-map(あれば)、コードベース(実現手段の確認のため)
- 同じ親 Issue の他の単位の実現案(インターフェース契約を揃えるため)

読んではいけないもの:
- 変更履歴の往復の中身(結論だけが本文に蒸留済み)
- 会話履歴

## 手順

1. **候補を2つ以上立てる** 1案しか無い状態で書き始めない。却下案が無い実現案は比較の痕跡が無く、違和感の検出器として働かない
2. **目次表を書く** T 行ごとに「対応可否 / 対応内容 / 機能単位」を付ける。対応可否は「あり」か「なし(Tn で達成)」「なし(既存の〜で達成)」の短い語だけ。変更なしの理由はここに集約する。原因未確定などで本案では途中までしか満たせない T は「本案は〜まで。残りは次段で確定」と範囲を書く(空欄にも、満たす振りにもしない)。表の直後に「実装が要るのは Tn, Tm だけ」を1行置く
3. **機能単位の節を書く** 変更がある機能単位(画面/クエリ/バッチ/マスタ等)だけ。節ごとに「何を、どう変えるか」を利用者の語で3〜5行。変更なしの機能は節を作らない
4. **図を描くか決める** 機能単位が3つ以上、または単位間に依存があるときだけ描く。描かないなら「図: 省略(単一機能のため)」と明記する。描くときの型:

   | 変更タイプ | 型 | Mermaid |
   |---|---|---|
   | 画面 | Before / After の状態遷移 | `stateDiagram-v2` を2枚 |
   | API | シーケンス + スキーマ差分 | `sequenceDiagram` + 差分表 |
   | IaC | 構成図の差分 | `flowchart` で追加を `:::add`、削除を `:::del` |
   | データ | 流れの Before / After | `flowchart LR` を2枚 |

   ノードのラベルは利用者の語(利用者・入口・振る舞い)。クラス名・設定キー・ライブラリ名は使わない
5. **根拠・却下案・⚠を書く** 根拠(なぜこの案か)、却下案(1案1行)、⚠(最大3。「何が崩れると案が成り立たないか」の形)。⚠ は実現案固有のものだけ。要件側の⚠に依存するときは番号で参照して再掲しない
6. **実装メモ(AI 用)を書く** 触るファイルと順序、インターフェース契約(分割時のみ。API スキーマ・ファイル形式・イベント名を凍結)、検証コマンド。実装語彙はここにだけ書く。省略しない(人間向け本文に溶かすと抜ける)
7. **分割する(必要なら)** 子 PR は単体で既定ブランチにマージできる単位。先行分を先にマージする前提で順序を書く。積み上げ PR にしない
8. **出力** 下の書式でコメント文面を提示する。初版の見出しは「実現案(draft)」、承認後の差し替えで「実現案」にする。差し替えのたびに修正履歴に1行足す

試走でローカルファイル `<name>.md` を対象にする場合は、作業用ディレクトリの `<name>.proposal.md` に書く。

## 出力書式

以下は骨格(外側の `~~~~` は出力に含めない)。

~~~~
## 実現案(draft)

### 受け入れ基準と対応
| ID | 受け入れ基準 | 対応可否 | 対応内容 | 機能単位 |
|---|---|---|---|---|
| T1 | … | あり | 一覧に絞り込みを追加 | 一覧画面 |
| T2 | … | なし(T1 で達成) | | |
| T3 | … | なし(既存の権限チェックで達成) | | |

実装が要るのは T1 だけ。

### 一覧画面
(何を、どう変えるか。3〜5行)

### 図
省略(単一機能のため)

### 根拠・却下案・⚠
- 根拠: …
- 却下案: 案B=…(却下理由)
- ⚠1: …

<details><summary>実装メモ(AI 用)</summary>

- 触るファイルと順序: …
- インターフェース契約(分割時のみ): …
- 検証コマンド: …

</details>

<details><summary>修正履歴</summary>

| 版 | 日付 | 変更 |
|---|---|---|

</details>
~~~~

## よくある失敗

- 図を先頭に置く → 「何の図か分からない」。目次表が先。図は任意
- 目次表で「変更なし」が文末にある → 全行読まないと実装が要る行が分からない。対応可否を列として先頭側に置き、表の直後に「実装が要るのは Tn だけ」を書く
- 変更なしの理由を目次と機能単位の両方に書く → 重複。目次の対応可否欄だけ
- 実装メモを省く、または本文に溶かす → AI 向けの情報(ファイル・順序・契約・検証)が抜ける。details で必須
- 本文に設定キー・環境変数名・フック名が出る → 実装メモへ
- リスクが「残課題」「注意点」として文中に散る → ⚠ として集め、3つに絞る
- 「判断してほしい点」として質問を並べる → 実現案は仮説の提示。解釈で埋めた箇所は⚠に書く。ビジネス判断が本当に要るなら req-3 に差し戻す
- 見出しに「ゲート②」「L1」 → Issue 向けの語。「実現案」だけ
- 段取りと工数見積りを書く → 承認の対象ではない。書くなら実装メモ
- 2段の積み上げ PR → CI・rebase・生成物更新が段の数だけ発生する。単体でマージできる単位に切り直す
