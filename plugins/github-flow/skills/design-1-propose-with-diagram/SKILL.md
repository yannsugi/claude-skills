# design-1-propose-with-diagram

設計レイヤの1番目。承認済みの受け入れ基準に対して「進み方」を提示し、人間が仮説として採択できる形にする。
思想は `${CLAUDE_PLUGIN_ROOT}/DESIGN.md` の「実現案の提示仕様」節。実現案は違和感の検出器として設計する。

**核**: 目次表(T ごとの対応可否)だけで「どこに実装が要るか」が分かること。実現案はその Issue で完結させ「何をしなければならないか」だけ書く。人間向けの本文と AI 向けの実装メモを混ぜない。却下案と⚠懸念点を自分で名指しする。

## 入力契約

`${CLAUDE_PLUGIN_ROOT}/references/principles.md` に従う(出力先・書式・技術事実の断定・分割の条件)。

読んでよいもの(全列挙):
- 対象 Issue の「## 実装前の要件・受け入れ基準の整理」節(承認済み)と「## コンテキスト(エージェント参照用)」節(調査結果・技術判断の根拠)
- system-map(あれば)、コードベース(実現手段の確認のため)
- 同じ親 Issue の他の単位の実現案(インターフェース契約を揃えるため)

読んではいけないもの:
- 変更履歴の往復の中身(結論だけが本文に蒸留済み)
- 会話履歴

書いてはいけないもの(読んでも本文に出さない):
- 他の子 Issue・親 Issue・要件確認への言及(依存・共有・凍結)。決まった事実(方針・入力データの形)は、その Issue の語で直接書く
- 読み手が辿れない前例(他 Issue・他 repo・別契約者)。repo 内ファイルの前例だけを実装メモに書く

## 本文の語

人間向け本文で避けるのは、クラス名・関数名・設定キー・環境変数名など、コードを読まないと分からない語だけ。チームで共有されている技術語(ライブラリ名・基盤名・サービス名)は言い換えない(「旧実装と新実装」のような言い換えは何の話か分からなくなる)。データ構造の変更は、本文では方針の粒度(何をどの形で持つか・未設定の扱い・既存データの扱い)で書き、列名・型は実装メモに書く。

## 手順

1. **候補を2つ以上立てる** 1案しか無い状態で書き始めない。却下案が無い実現案は比較の痕跡が無く、違和感の検出器として働かない
2. **目次表を書く** T 行ごとに「対応可否 / 対応内容 / 機能単位」を付ける。対応可否は「あり」か「なし(Tn で達成)」「なし(既存の〜で達成)」の短い語だけ。変更なしの理由はここに集約する。原因未確定などで本案では途中までしか満たせない T は「本案は〜まで。残りは次段で確定」と範囲を書く(空欄にも、満たす振りにもしない)。表の直後に「実装が要るのは Tn, Tm だけ」を1行置く
3. **機能単位の節を書く** 変更がある機能単位(画面/クエリ/バッチ/マスタ等)だけ。節ごとに「何を、どう変えるか」を利用者の語で3〜5行。変更なしの機能は節を作らない
4. **図を描くか決める** 機能単位が3つ以上、または単位間に依存があるときだけ描く。描かないなら「図: 省略(単一機能のため)」と明記する。描くときの型:

   | 変更タイプ | 型 | Mermaid |
   |---|---|---|
   | 画面 | Before / After の状態遷移 | `stateDiagram-v2` を2枚 |
   | API | シーケンス + スキーマ差分 | `sequenceDiagram` + 差分表 |
   | IaC | 構成図の差分 | `flowchart` で追加を `:::add`、削除を `:::del` |
   | データ | 流れの Before / After | `flowchart LR` を2枚 |

   ノードのラベルは利用者の語(利用者・入口・振る舞い)。クラス名・設定キー・ライブラリ名は使わない
5. **設計判断の根拠・⚠懸念点を書く** `### 設計判断の根拠・⚠懸念点` の下に `#### 設計判断の根拠` と `#### ⚠懸念点` の 2 段。各項目は太字見出し 1 行(結論)+ネストした説明(1 文 1 項目)。懸念は `**⚠1. 見出し**` で採番する
   - 根拠は「なぜこの案か」。読み手が辿れない前例(他 Issue・他 repo・別契約者)は書かない
   - ⚠懸念点は「案が成り立たなくなる条件」と「利用者・運用に見える副作用」だけ。開発者が通常確認する事項、未リリース機能への影響、既存機能の性質上避けられない挙動は書かない
6. **却下案を書く** `<details><summary>却下案(採らなかった案)</summary>` に 1 案 1 行(案と却下理由)。実装メモの前に置く。比較の痕跡として残すが、採用案の読み取りを邪魔しない
7. **実装メモ(AI 用)を書く** 触るファイルと順序、インターフェース契約(API スキーマ・ファイル形式・イベント名・列名・型)、repo 内の前例ファイル、検証コマンド。実装語彙はここにだけ書く。省略しない(人間向け本文に溶かすと抜ける)
8. **分割する(必要なら)** 子 PR は単体で既定ブランチにマージできる単位。先行分を先にマージする前提で順序を書く。積み上げ PR にしない
9. **出力** 下の書式でコメント文面を提示する。初版の見出しは「実現案(draft)」、承認後の差し替えで「実現案」にする。差し替えのたびに修正履歴に1行足す

試走でローカルファイル `<name>.md` を対象にする場合は、作業用ディレクトリの `<name>.proposal.md` に書く。

## よくある失敗

- 図を先頭に置く → 「何の図か分からない」。目次表が先。図は任意
- 目次表で「変更なし」が文末にある → 全行読まないと実装が要る行が分からない。対応可否を列として先頭側に置き、表の直後に「実装が要るのは Tn だけ」を書く
- 変更なしの理由を目次と機能単位の両方に書く → 重複。目次の対応可否欄だけ
- 実装メモを省く、または本文に溶かす → AI 向けの情報(ファイル・順序・契約・検証)が抜ける。details で必須
- 本文に設定キー・環境変数名・フック名が出る → 実装メモへ
- リスクが「残課題」「注意点」として文中に散る → ⚠懸念点に集める
- ⚠懸念点に「開発者が担保すべき普通のこと」(既存テストを通す、マイグレーションを確認する)を書く → 案固有の崩れ方と利用者に見える副作用だけ
- 根拠と懸念を 1 節に並べ、根拠を長い 1 項目に詰める → 2 段の小見出しに分け、各項目は結論 1 行+ネストした説明
- 却下案を根拠・懸念と同じ節に並べる → details に折りたたむ
- 他の子 Issue・親 Issue・要件確認に言及する(「子2 と共有」「要件確認 B の回答待ち」) → その Issue で完結させ、決まった事実をその Issue の語で書く
- 「旧実装と新実装」のようにチームの共有語(ライブラリ名)を言い換える → 共有されている技術語はそのまま。避けるのはコードを読まないと分からない語だけ
- 列名・型を本文に書く → 実装メモへ。本文は「何をどの形で持つか」の粒度
- 「判断してほしい点」として質問を並べる → 実現案は仮説の提示。解釈で埋めた箇所は⚠に書く。ビジネス判断が本当に要るなら req-3 に差し戻す
- 見出しに「ゲート②」「L1」 → Issue 向けの語。「実現案」だけ
- 段取りと工数見積りを書く → 承認の対象ではない。書くなら実装メモ
- 2段の積み上げ PR → CI・rebase・生成物更新が段の数だけ発生する。単体でマージできる単位に切り直す
