# req-1-triage-issue

要件レイヤの1番目。Issue を S / M / L に判定し、根拠を一行と、完了基準(C1〜Cn)を Issue から拾って残す。判定と C は後続の全工程の背骨になる。
思想は `${CLAUDE_PLUGIN_ROOT}/DESIGN.md` の「要件レイヤの規律」冒頭。

**核**: 判定・根拠一行・完了基準の採番だけを出す。原因の仮説・修正案・次の一手は出さない(後続の判断を汚染する)。

## 入力契約

`${CLAUDE_PLUGIN_ROOT}/references/principles.md` に従う(出力先・書式・技術事実の扱い)。

読んでよいもの: 対象 Issue の本文(`gh issue view <n>`)、対象 repo のディレクトリ構成と README、system-map(あれば)。
読んではいけないもの: 他 Issue、実装コードの中身(構成を見るのはよいが、原因を追って読み込まない)。README を読んで原因の仮説が浮かんでも、根拠には書かない。

## 判定基準

| 判定 | 基準 | 後続 |
|---|---|---|
| S | 影響が1領域・1入口に閉じ、受け入れ基準が報告文からほぼそのまま書ける | req-3 で要件整理と実現案を1コメントに畳む軽量経路。承認は省かない |
| M | 影響領域は見当がつくが、受け入れ基準を書くには現状調査が要る | 標準経路(req-3 →) |
| L | 影響領域が複数に跨る、または跨るかどうかが分からない。分割が必要になりそう | req-2 を前置してから標準経路 |

迷ったら上へ倒す。L 相当を M と誤ると、調査不足のまま分割して多単位で前提崩壊する。

領域 = FE / BE / IaC / データ。repo に無い領域は数えない(compose とスクリプトだけの repo なら IaC とデータの2領域で見る)。入口の数と領域の数が食い違うときは領域の数を優先する。判定に使った領域と、改修か新規かを根拠に含める。

## 手順

1. Issue 本文を読み、報告されている入口(画面・API・ファイル経路)と領域を挙げる
2. **完了基準を採番する** Issue が「できたら終わり」と言っていることを C1〜Cn に分ける。Issue の語をそのまま使い、言い換えない。書かれていないことは足さない(足したくなったら req-3 の要件確認に回す)
3. ディレクトリ構成と README、system-map から、その入口に関わる領域が1つか複数か、それとも分からないかを見る。所要時間の目安は5分。原因を探し始めたら止める
4. 判定と根拠一行を決める(目安100字)。根拠の型: `<判定>: <改修/新規>・領域=<…>・<複数領域か/不明か/1領域か>・<迷った点があれば一語>`
5. 次のブロックを成果物として提示する。L なら、req-2 への引き継ぎとして「各 C を既存機能で満たせるか調べる」を次の行に書く

```
## トリアージ
- 判定: L
- 根拠: 改修・領域=IaC+データ・対象環境が検証用か運用系か本文から確定せず影響領域不明・上に倒した
- 完了基準: C1 検証環境でも同じ手順で起動できる / C2 起動手順が README に載っている
- 次: req-2-survey-codebase(C1・C2 それぞれを既存機能で満たせるか調べる)
```

試走でローカルファイル `<name>.md` を対象にする場合は、作業用ディレクトリの `<name>.triage.md` に上記ブロックを書く。

## よくある失敗

- 根拠が3行を超える → 要件整理を始めている。判定に効いた事実だけ残して削る
- 「仮説 A/B」「切り分け順」「推奨する次の一手」を書く → 実現案の語彙。全部削る
- 「1行直せば終わりそう」で S にする → 修正量は基準ではない。影響領域の数と確定度が基準
- S の理由に「急いでいるから」が混じる → 判定は Issue の性質で決める。速度は経路の畳み方で出す
- C に Issue に書かれていない基準(監視・恒久対策)を足す → スコープ拡張。req-3 の要件確認へ
