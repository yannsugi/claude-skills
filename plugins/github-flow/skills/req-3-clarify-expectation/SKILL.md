# req-3-clarify-expectation

要件レイヤの3番目。Issue の曖昧さを解消し、人間が承認できる「実装前の要件・受け入れ基準の整理」に落とす。
思想は `${CLAUDE_PLUGIN_ROOT}/DESIGN.md` の「要件レイヤの規律」「Issue の2部構成」節。

**核**: 人間に届くのはビジネス判断だけ。受け入れ基準は E2E で観測できる語彙だけで、初版から格子と表で出す。

## 入力契約

`${CLAUDE_PLUGIN_ROOT}/references/principles.md` に従う(出力先・書式・技術事実の断定・C/T の採番・分割の条件)。

読んでよいもの(全列挙):
- 対象 Issue の本文・コメント(`gh issue view <n> --comments`)、および Issue 内リンク先。トリアージ結果(C1〜Cn)と網羅的調査の結果はここに含まれる
- コードベース(README・設計メモを含む。現状調査のため。読んだ事実は「コンテキスト > 調査結果」へ)
- `assets/expectation.md`(出力書式)と `assets/questions.md`(要件確認の書式)

読んではいけないもの:
- 他 Issue の実現案・実装 PR(解釈が引きずられる)
- 会話履歴。前回までの往復は本文と変更履歴に蒸留済みとみなす

## 手順

1. **トリアージ結果を読む** 判定・根拠・完了基準(C)を転記する。未判定なら先に req-1 を実行する。L で req-2 の結果が無ければ先に実行する(未確認セルは⚠候補として受け取る。「既存で満たせる C」はその入口を受け入れ基準に使う)。S なら要件整理と実現案を1コメントに畳んでよいが、承認は省かない
2. **業務背景を書く** その機能が業務上何で、誰がいつ使うか。3〜5行
3. **現状調査** 改修/新規、FE/BE/IaC/データの領域判定。事実は調査結果へ、仮説は仮説と明記。要件確認・⚠・制約に載せる技術事実は principles.md の手順で囲みブロックを読んでから書く
4. **格子を作る** 行=Given(状態)、列=When(操作)。列には Issue に無い既存操作(取消・一括処理・再実行・権限の無い利用者の操作など)を既定で並べる。全セルを埋める: T の ID / 対象外(理由) / 要件確認の ID。次の2種類のセルは1つずつ声に出して確認する
   - ルールが効かない側: 未設定のまま通る、条件を満たさない利用者が開く、既存データが古い形のまま
   - 埋まらないセル: Issue が何も言っていない → 要件確認の候補
5. **受け入れ基準の表を書く** 格子のセルと1対1で T 行を書く(ID/基準/Entry/Actor/Given/When/Then/Issue/E2E)。Entry は GUI に限らない。各 T は C のどれかに対応させる。対応する T が無い C は完了基準の表に理由を書く
6. **質問ルーター** 湧いた疑問を3分類してから動く
   | 分類 | 判定基準 | 処理 |
   |---|---|---|
   | ビジネス判断 | 調べても決まらない。利用者・業務・優先度・スコープの選択 | 要件確認へ(`assets/questions.md` の書式) |
   | 技術判断 | コード・ログ・設定を読めば決まる | 自分で調べて決め、根拠を「技術判断の根拠」へ |
   | 些末 | どちらでも品質に効かない | デフォルト案で進め「些末判断」に記録(通知のみ) |
   ビジネスか些末かで迷ったときだけ聞く側へ倒す。技術判断を人間に投げない。Issue の要件を置き換える提案は求められたときだけ出し、既定は Issue どおりの認識+代替案1行にする
   回答を待たずに進める場合、暫定値は変更履歴に「暫定・回答待ち」と記す。些末判断には書かない(業務判断を些末に見せない)
7. **E2E 語彙プリフライト** T 行・制約・非機能を検査:
   - E2E(画面操作・API 呼び出し・ファイル着信・ログ出力)で観測できない行 → 書き直すか、コンテキストへ移す
   - クラス名・ライブラリ名・テーブル名・環境変数名などの実装語彙 → コンテキストへ移す
   - ⚠ は3つまで、各1〜2文+補助表1つ。超えたら統合するか、確信の低い順に残す。あふれた解釈は変更履歴に「暫定」として残す
8. **分割する(必要なら)** 子 Issue の表は「検証できる基準」を T の ID だけで書く。実装を伴わない確認行は「親」にまとめる。各子 Issue は単体で既定ブランチにマージできる単位にし、先行分を先にマージする順で並べる
9. **変更履歴** 初版でも1行書く。2回目以降は「どの回答・調査結果を受けて、どの行が変わったか」。details の中に置く
10. **出力** 新しい本文を成果物として提示する。2回目以降は「変わった行」の差分も添える。呼びかけ文は書かない

試走でローカルファイル `<name>.md` を対象にする場合は、作業用ディレクトリに本文を `<name>.expectation.md`、要件確認を `<name>.questions.md` として書く。

## よくある失敗

- 初版が散文の Asis/Tobe → 読まれず、表に作り直すまで往復が増える。初版から格子と T 表を出す
- 要件確認が5つ以上ある → ルーターを通していない。技術判断と些末を引き戻す
- Then に「原因」「修正方法」が書いてある → 実現案の語彙。Then は振る舞いだけ
- 格子に「ルールが効かない側」の行が無い → 未設定のまま通る経路を見落とす。行を足して1セルずつ確認する
- grep の行番号だけで「設定 X の内側」と書く → 囲みブロックを読んでいない。読めなければ⚠に落とす
- 影響画面に内部サービス名やコンテナ名が並ぶ → 利用者から見える入口に言い換える。利用者が実際に叩く接続先(URL・ポート・エンドポイント名)は入口なので書いてよい
- 出典にローカルパスを書く → Issue/Slack の URL を書く。手元のパスは調査結果へ
- 報告に無い要求(監視・恒久対策)を T に足す → スコープ拡張はビジネス判断。要件確認にして待つ
- 見出しに「期待」「ゲート①」、本文に「ご確認ください」 → Issue 向けの語で書く。記録であって承認依頼ではない
