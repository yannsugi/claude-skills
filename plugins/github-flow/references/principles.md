# 共通原則

github-flow の全スキルが従う。各 SKILL.md はこのファイルを入力契約に含める。

## 出力先

| 状況 | 出力先 |
|---|---|
| 既定 | 作業用のメモ置き場(呼び出し側が指定したディレクトリ。無ければ対象 repo 外の一時ディレクトリ)。文面を提示して止まる |
| repo への書き込み(system-map・設計メモ・コミット) | 利用者が明示的に指示したときだけ |
| GitHub への書き込み(`gh issue comment` / `gh issue edit` / `gh pr comment` / ラベル) | 利用者が明示的に指示したときだけ |

読み取り(`gh issue view` / `gh pr diff` 等)は自由。成果物の本文中で参照するパスは対象 repo のルートからの相対で書く。

## 書式

- 表にできるものは表にする。散文は、表の読み下しと背景説明にだけ使う
- 見出しは利用者の語で書く。「ゲート②」「L1」などフロー用語は Issue コメントに書かない
- 呼びかけ文(「ご確認ください」など)は書かない。記録として読める形にする
- 確認する相手を役割名(「PM」など)で呼ばない。節の名前は「要件確認」

## 技術事実の断定

要件確認・⚠・制約・根拠に載せる技術事実は、次の手順で確定する。

1. grep の一致行だけで断定しない。一致行を囲むブロック(関数・条件分岐・設定の親キー)を読む
2. ゲート・フラグ・権限に関する主張(「設定 X の内側で動く」「権限 Y が無いと通らない」)は、ブロックを読んでも確信を1段下げて書く(「〜と読める」)。囲みを読めなかったものは⚠にする
3. 並列エージェントや要約を経由した事実は、根拠行(ファイルパス:行と原文の抜粋)を要約で落とさない。ゲート・フラグ・権限の行は必ず原文を残す

## マスタ・seed・fixture

コード内のマスタ・seed・fixture は実運用のデータと一致しない前提で扱う。それを根拠に使うときは「正の所在(本番 DB・運用手順書など)は未確認」と明記する。

## ツール

ファイルの作成・編集は専用の編集ツールで行う(`sed` や heredoc で書き換えない)。権限設定で許可された実行形式に合わせ、確認待ちで止まらないようにする。

## 完了基準(C)と受け入れ基準(T)

| 記号 | 意味 | 採番する工程 | 使う工程 |
|---|---|---|---|
| C1〜Cn | Issue が「できたら終わり」と言っていること(完了基準) | req-1-triage-issue | req-2 の調査、req-3 の対応表 |
| T1〜Tn | E2E で観測できる受け入れ基準(Given/When/Then) | req-3-clarify-expectation | design-1 の目次表、子 Issue、verify-1 の照合 |

T の ID は工程を跨いで変えない。子 Issue・実現案・E2E テストは T の ID で参照する。

## 分割の条件

子 Issue / PR に分けるときは「単体で既定ブランチにマージできる単位」で切る。先行分を先にマージする前提で順序を書く。積み上げ PR(前の PR の上に次を積む)にしない。単体で成立しない分割は分解し直す。
