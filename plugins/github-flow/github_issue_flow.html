GitHub Issue解決フロー

方針：開発者の労力を最小に（将来の労力を含む通時的最小化）、最大の品質を。承認は労力ではなく理解を生産する投資。GitHub＝具体、Slack＝抽象。人間は散文を読まない — 承認の対象は表と格子で出す。本図とDESIGN.mdは試走の観測に合わせて常に書き直す（過去の版はgitにある）。

人間が理解するのはこの3点だけ

  • 要件の正しさ（ゲート①）— 問題を正しく捉えたか。読むのは完了基準C・受け入れ基準Tの表・状態×操作の格子
  • 判断の方向（ゲート②）— 進み方は妥当か（承認＝仮説の採択。実装は反証実験）。読むのはTごとの対応可否の目次表
  • 翻訳の一致（ゲート③）— TがテストにE2Eで正しく落ちたか。読むのはT→テスト対応表とテストコード

実装は人間が読まない。代わりに観測と指標が担保する

  • 実装の正しさ → E2Eの観測（AIの誠実さと無関係に真）
  • 実装の健全性 → 前提崩壊率（内部の腐敗の遅行指標）
  • 性善説は「承認の判断」にのみ適用。信用が必要な面積を最小化して残りに適用する
AIが実行 人間ゲート 例外・差し戻し 資産・メタループ 世代交代 コンテキスト規律
トリアージ req-1-triage-issueS / M / L 判定＋根拠を一行記録＋完了基準 C1〜Cn をIssueの語のまま採番（Cが後続全工程の背骨）
  • S：軽量経路（要件整理と実現案を1コメントに畳む。承認は省かない — 理解コストが小さいから速いだけ）
  • M:標準経路（下記フルフロー）
  • L:網羅的調査を前置してからフルフロー。「各Cを既存機能で満たせるか」を調査へ渡す
誤判定はNG調査の帰属先の一つ（L相当をMと誤ると調査不足のまま分割し多単位で崩壊する）
網羅的調査 req-2-survey-codebaseLのみ・最大分割の前提条件
  • 領域×観点マトリクス（FE/BE/IaC/データ × 参照/変更/暗黙の依存）の全セルを「確認済み/未確認」で埋める — 網羅の定義を先に固定し自己申告を検証可能にする
  • 上層＝Cごとの3問表（既存で満たせるか／新規の仕組みが要るか／repo外依存）＋新規成果物の種類ごとの直近の前例1件。下層＝影響マップ（つながり＝直接/経由/関係しうる）
  • システムマップを起点に差分確認（全量探索は初回のみ）。並列サブエージェントで領域ごとに探索し集約。ゲート・フラグ・権限の行は原文の根拠行を残す
  • 未確認セルは⚠として要件側に浮上し、ゲート①で人間の目に入る。マスタ・seedは実運用と一致しない前提
産物：C表＋前例＋マトリクス＋影響マップ → システムマップへ還元（出力先は作業メモ。repoへは明示指示時のみ）
要件整理 req-3-clarify-expectation曖昧さの解消＋問題の最大分割。Issue見出しは「実装前の要件・受け入れ基準の整理」
  • 業務背景3〜5行 → 現状調査（改修/新規、領域判定。技術事実は囲みブロックを読んでから断定）
  • 状態×操作の格子：Given×Whenに既存操作（取消・一括・権限なし）を既定で並べ、全セルをT／対象外／要件確認で埋める。「ルールが効かない側」のセルを1つずつ確認
  • 受け入れ基準の表（ID/基準/Entry/Actor/Given/When/Then/Issue/E2E）：格子のセルと1対1。Cとの対応表を直前に置く。初版から表で出す
  • 質問ルーター：ビジネス判断→要件確認（平坦なID＋「認識どおり/違う」、1問3文以内）／技術判断→調査で自己解決／些末→デフォルト案＋通知
  • 最大分割：独立に検証可能かつ単体でマージできる単位へ。子IssueはTのIDで参照。切れない結合は統合期待として親に残す。変更履歴は3列でdetailsへ
産物：要件・受け入れ基準の整理（実装語彙を含まない）＋要件確認＋分割表＋コンテキスト。呼びかけ文・フロー用語は書かない
ゲート① C/T表＋格子＋要件確認＋分割の承認 — 2回目以降は変わった行の差分中心。人間は「問題を正しく捉えたか」と要件確認への回答だけ
分配ポイントA（垂直・原則）：承認済みの受け入れ基準の単位（子Issue）ごとに担当（人間/エージェント）へ配り、以降のパイプラインを丸ごと持たせる。契約が凍結された地点でのみ安全に並列化できる — 要件整理自体は分配不能（曖昧なまま配ると解釈が人数分に複製される）
実現案 design-1-propose-with-diagram単位ごと
  • 候補を2つ以上立ててから書く（コンテキスト＋マップ＋同じ親の他単位の実現案を判断材料に）
提示仕様（違和感の検出器として設計する）
  1. 目次表が先：Tごとに対応可否／対応内容／機能単位。可否は「あり」「なし（Tnで達成）」の短い語だけ。直後に「実装が要るのはTnだけ」を1行
  2. 変更がある機能単位（画面/クエリ/バッチ/マスタ）だけ節を書く。利用者の語で
  3. 図は任意：機能単位が3つ以上か依存があるときだけ。描かないなら「省略」と明記。描くなら変更タイプ別の型（画面→Before/After状態遷移、API→シーケンス＋スキーマ差分、IaC→構成図差分、データ→流れのBefore/After）
  4. 根拠・却下案＋却下理由・⚠の名指し（予算：最大3）
  5. <details>実装メモ（AI用）</details> 必須：触るファイルと順序・インターフェース契約・検証コマンド。人間向け本文と混ぜない。末尾に修正履歴
ゲート② 実現案の承認 ＝ 現在の知識で最善という仮説の採択。実装はその反証実験。差し戻しは失敗ではなく想定内動作
分配ポイントB（水平・単位が大きすぎる時のみ）：実現案が定義したインターフェース契約（APIスキーマ等）に沿って実装だけを分ける。契約凍結前の水平分割は禁止。子PRは単体で既定ブランチにマージできる単位（積み上げPRにしない）
実装 単位ごと
  • 承認済み実現案の実装メモ（AI用）に沿って実行（Opus 5.5）。実装は純粋な実行ではなく最後の調査フェーズを兼ねる
  • 前提崩壊の申告プロトコル：「前提Xが崩れた。現地はこうだ」と申告して停止することを正常な出力として定義。回避策を積んで実現案を守り抜かない（隠すコストが最も高い）
3方向差し戻し（崩れたものの種類で分岐）
  • 実現案の選択が誤り → ゲート②へ。却下理由を背景に追記（同じ袋小路に二度入らない）
  • 要件の前提が誤り → ゲート①へ。変更履歴に「実装時の発見により改訂」
  • 負債が独立した障害物 → 実行時分割：負債解消単位＋機能単位（依存）に切り、それぞれ通常フローへ
前提崩壊はマップの該当項目を同時修正（例外系更新）。崩壊率は領域別に集計 → コードベースの健康診断指標・負債返済Issueの起票根拠
品質担保 verify-1-traceability単位ごと＋統合
  • E2Eテスト：Tの各行→観測可能な振る舞いへ翻訳。統合期待は親Issue側で検証
  • T→テスト対応表＋エビデンス（スクリーンショット・実行ログ）— 全行カバーの機械的証明。TのIDはそのまま使う。判定はcovered/uncovered/escalateの3値のみ
  • 実装図解の機械突合・システムマップdiff生成は未実装（図が任意になったため、必要になったら設計し直す）
ゲート③ フィードバック（2モード） — 人間が読むコードは実装ではなくテストコード（Tと同じ語彙で書かれ、AIの解釈が最も裸で現れる場所）
育成モード（初期）対応表＋テストコードを厳格にチェック。「このケースはダメ」「この実装だと〜が起きる」を具体的に出す → 資産へ変換。⚠に挙がっていなかった指摘の率を計測（検出漏れの実測） 巡航モード（成熟後）対応表のみ。移行条件：⚠外指摘率が十分低下。移行を急がないことが性善説の担保
PRマージ 小さなPRの束
  • 要件整理の文書はクローズ（短命）、背景・決定・evalは資産へ（長命）。各PRは単体で既定ブランチにマージできる
  • QAフェーズ（後続）のNGはNG調査へフィードバック

例外フロー：NG調査

承認済み成果物を境界に証拠連鎖を逆向きに二分探索。分割済みのため爆風半径は1単位。

Tに書かれていない→ 要件整理の欠陥。人間の再承認イベント
実現案・実装が乖離→ 差し戻しリトライ。Tは不変
テストが未検出→ テスト観点の漏れ
トリアージの誤判定→ 判定基準の改訂
プロセスの誤り→ 資産改訂（宛先つきdiff提案）

資産（沈殿先）

evalセット永続資産の本体。実運用Issueが素材。SKILL.mdより長生きする仕様
システムマップ索引であって本文ではない（場所・関係・鮮度のポインタ集。要約の転記禁止）。鮮度メタデータ必須：最終確認Issue＋日付、古い項目は「未確認」へ自動降格。更新3経路＝マージ時（正常系）／前提崩壊時（例外系）／網羅的調査時（探索系）。内容は事実のみ＝人間ゲート不要、スキーマ変更のみ資産diffとして承認
assets（要件整理・要件確認の書式）／references/principles.md／SKILL.md群世代ごとに書き直す実装。試走の指摘はここへ還元する
CLAUDE.md・コンテキスト文書コードから読めない恒久知識
決定ログ仕分け結果・フェーズ別NG混入率・前提崩壊率の集計元

コンテキスト最小化（実行時の規律）

コンテキストは渡さず、取りに行かせる。マップはその索引。

フェーズ別入力契約各SKILL.md冒頭に「読んでよいもの」全列挙＋「読んではいけないもの」明記。例：突合役に実現案の判断理由を読ませない（採点が甘くなる）— 最小化は独立性の注入でもある
フェーズ間は成果物のみ会話履歴を持ち越さない。往復は要件整理の文書と変更履歴に蒸留された時点で役目を終える。CとTのIDが工程を跨ぐ唯一の参照
出力先は作業メモrepo・GitHubへの書き込みは明示指示があるときだけ。技術事実は囲みブロックを読んでから断定し、根拠行を要約で落とさない
予算の計測フェーズ別トークン・読了ファイル数を試走から記録。契約外読込は契約かマップの欠陥としてメタループへ

世代交代ループ（skill-gardener）

モデル更新を検知したらスキルを剪定する。ドメイン知識は残し、旧モデルの欠陥補正だけを削る。

1. 新モデルでeval再実行使用頻度・NG混入率の高い順
2. Ablation指示ブロック単位で抜いて再eval。抜いても落ちない＝削除候補
3. 新モデル特有の失敗へ補正提案
4. diff提案→人間承認gardener自身の改訂は人間レビューを厚く（自己言及禁止）
メタループ（当面は週次の手動棚卸し）：解明の訂正履歴（事前の予防接種）＋育成モードの具体的指摘＋QA NG＋NG混入率＋前提崩壊率＋コンテキスト予算が、資産diffへ沈殿。フェーズ別混入率が投資判断と育成→巡航移行の根拠。世代交代ループが資産をモデル更新のたびに剪定し、evalセットだけが世代を越えて生き残る。

スキルとモデル割当

スキルの実行はすべてOpus 5.5（各SKILL.mdのmodel:で指定。Opus 5よりラリー回数が少なく、Fableと使用感に大差がなくコストが低い）。判定役＝evalの採点・verify-1からのエスカレーション先・ゲートで人間を補助する読み手はFable 5.1。evalは常に実際に使うモデルで実行し、割当は運用パラメータとして更新する。スキル名の先頭はレイヤ（req / design / verify）とレイヤ内の順序。
スキル担当モデル割当理由
req-1-triage-issue S/M/L判定・根拠一行・完了基準C1〜Cnの採番 Opus 5.5 判定と採番だけ。原因の仮説を書かない規律が主
req-2-survey-codebase 網羅的調査（L経路）・Cごとの3問表・前例・マトリクス消込・影響マップ・マップ更新 Opus 5.5 網羅的探索の正確性勝負。領域別に並列サブエージェント→集約（根拠行を落とさない）
req-3-clarify-expectation 業務背景・格子・受け入れ基準T表・質問ルーター・要件確認・分割・変更履歴・E2E語彙プリフライト Opus 5.5 曖昧さの検出がフロー全体の品質上限。初版から表で出す
design-1-propose-with-diagram 実現案（Tごとの目次表・機能単位・図は任意・根拠/却下案/⚠・実装メモ） Opus 5.5 候補2案以上の比較と違和感検出器の生成
（実装） 自作スキルなし。実装メモ（AI用）＋前提崩壊申告プロトコル Opus 5.5 決まったことを決まった通りに
verify-1-traceability T→テスト対応表・エビデンス・未カバー・エスカレーション Opus 5.5 照合のみ。迷う差分は判定役（Fable 5.1）か人間へ
（判定役） evalの採点・エスカレーションの裁定・ゲートで人間を補助する読み手 Fable 5.1 実行役と採点役を分け、自己採点の相関を切る
attribute-defect（未実装） NG調査・帰属・改訂diff提案 Fable 5.1 因果推論と抽象化。低頻度・高価値。痛みを観測してから
distill-feedback / skill-gardener（未実装） ゲート③指摘の資産diff化・モデル更新時のeval再実行とablation剪定 Fable 5.1 個別→一般則の昇華と剪定判断。当面は手動棚卸し

今の状態

  • 要件（req-1/2/3）→設計（design-1）→検証（verify-1）がスキルで通る。実装は素のClaude Code＋実装メモ
  • 各工程の産物は表。CとTのIDが工程を跨ぐ参照。出力先は作業メモ、repo/GitHubへは明示指示時のみ
  • 独立レビューを1箇所：マージ前に要件整理の文書と実装だけを渡した別コンテキストのレビュー（実現案・対応表を見せない）— 自己採点の相関を切る最安の手段

試走で観測すること（eval素材）

  • 要件整理の往復回数（初版が格子と表で出たか）
  • 各ゲートの承認時間と読み味（⚠外指摘率）
  • 前提崩壊の有無・QA NGの有無
  • フェーズ別コンテキスト消費（契約外読込は契約かマップの欠陥）
  • ⚠予算3の適正・マップの鮮度閾値・Sの軽量経路の書式
