# GitHub Issue解決フロー — 設計思想(北極星 v3 準拠)

Claude Codeでの実装生成時に参照する思想文書。実装(SKILL.md等)はこの思想の
一表現にすぎず、モデル世代・コードベースに合わせて書き直してよい。
思想とevalセットが永続資産、実装は使い捨て。

図解版は `github_issue_flow_v3.html`(凍結版)。本文書はその文章版で、両者は同じ設計を指す。

## 核

- GitHubは具体(Issueに記載された確定した期待、PRマージによる解決の事実)、
  Slackは抽象(報告・要望・検討のコミュニケーション)。抽象→具体の翻訳だけが
  本質的に人間の判断を要する
- 方針:開発者の労力を最小に、最大の品質を。労力には**将来の労力**を含む —
  AIの判断を人間が判断できなくなる事態が最大のコスト
- 承認は労力ではなく、**理解を生産する投資**。高速化した開発に対して
  理解の速度を上げつつ品質を保つ仕組みである

## 3つのゲートと検証の分担

人間が理解するのは3点だけ:

| ゲート | 担保するもの |
|---|---|
| ① 期待の承認 | 問題を正しく捉えたか(期待+変更履歴+分割の差分レビュー) |
| ② 実現案の承認 | 進み方は妥当か(承認=仮説の採択。実装は反証実験) |
| ③ フィードバック | 期待がテストに正しく翻訳されたか(読むのはテストコード、実装ではない) |

実装そのものはどのゲートも読まない:

- 実装の**正しさ** → E2Eの観測が担保(AIの誠実さと無関係に真)
- 実装の**健全性** → 前提崩壊率(内部の腐敗の遅行指標)
- 性善説(想定と違えばNGを出すはず=承認をもって理解とみなす)は
  **承認の判断にのみ**適用する。信用が必要な面積を最小化し、残りに性善説を適用する

## 定常フローの骨格

トリアージ → (Lのみ)網羅的調査 → 解明 → ゲート① → 実現案 → ゲート② →
実装 → 品質担保 → ゲート③ → PRマージ。QAでのNGはNG調査へ還流。

## 解明フェーズの規律

- **トリアージ S/M/L**:根拠を一行記録(ゲート①で人間の目に入る)。迷ったら上に倒す。
  Sは工程を畳むが承認は省かない。Lは領域×観点マトリクス
  (FE/BE/IaC/データ × 参照/変更/暗黙の依存)の全セル消込が分割の前提条件
- **質問の3分類ルーティング**:人間に届くのはビジネス判断だけ。
  技術判断は調査で自己解決(根拠をコンテキストへ記録)、些末はデフォルト案+通知。
  ビジネスか些末かで迷ったときだけ聞く側に倒す
- **期待はE2Eで観測可能な語彙のみ**。観測不能な行は書き直すかコンテキストへ。
  期待に実装語彙(クラス名・ライブラリ名)が漏れたら分離の失敗
- **最大分割**:基準は「独立に検証可能な最小の期待単位」。実装の都合や数の多さは
  基準にしない。切れない結合は**統合期待**として親Issueに残す(過分割の安全弁)。
  依存グラフを親に記載(並列実行と作業分配の判断材料)
- **変更履歴**:どの調査結果・どの回答を受けて、どの行が、なぜ変わったか。
  承認は全文でなく差分と理由のレビュー。実装からの差し戻し(前提崩壊)もここに追記

## Issueの2部構成

- **期待**(人間承認の対象):Asis/Tobe・影響画面・制約・非機能・⚠(予算3)・変更履歴。
  短命 — マージでクローズ
- **コンテキスト**(承認不要・エージェント向け):Slackリンク・調査結果・技術判断の根拠。
  長命 — 人間は原則読まないが、参照の連鎖で辿れること

## 実現案の提示仕様(違和感の検出器として設計する)

1. 期待の語彙で書く(振る舞いの因果が主表現、実装語彙はL3へ)
2. 三層:L1=図1枚(ここだけでNG判断が成立)/L2=判断根拠と**却下案+却下理由**/
   L3=実装計画(人間は原則見ない)
3. ⚠の名指し(予算3):リスク・低確信・解釈の入った箇所をAI自身が宣言
4. 図形式は変更タイプ別に固定(読み慣れで承認が速くなる。省略で速くしない)

## 実装フェーズ

- 実装は純粋な実行ではなく**最後の調査フェーズを兼ねる**
- 前提崩壊の申告は正常な出力:「前提Xが崩れた。現地はこうだ」と申告して停止。
  回避策を積んで実現案を守り抜かない(隠すコストが最も高い)
- 差し戻し3方向:実現案の誤り→②へ(却下理由を資産化)/期待の前提の誤り→①へ
  (変更履歴に追記)/負債が障害物→実行時分割(負債解消単位+依存する機能単位)

## 品質担保

- 実装図解(実現案と同形式)→ 実現案図と機械突合。乖離=承認外変更の検知。
  「図解しか見ない」運用の前提を機械が担保する
- 期待→テスト対応表+エビデンス:期待の全行がE2Eで覆われることの機械的証明
- ゲート③は2モード:**育成**(図解+テストコードを厳格に。指摘は資産へ変換)→
  **巡航**(図解のみ。移行条件:⚠外指摘率の低下+突合の機械化の安定。移行を急がない
  ことが性善説の担保)

## 通底する原則

- 指摘はインスタンス(そのIssue)でなく資産(テンプレート・SKILL.md・CLAUDE.md・
  マップ)に還元する。人間はdiffの承認のみ
- コンテキストは渡さず取りに行かせる。フェーズ別に入力契約(読んでよいもの/
  いけないもの)を宣言。フェーズ間は成果物のみ受け渡し、会話履歴を持ち越さない。
  突合役に判断の物語を読ませない(最小化は独立性の注入でもある)
- システムマップは**索引であって本文ではない**(場所・関係・鮮度のポインタ集。
  要約の転記禁止)。鮮度メタデータ必須、古い項目は未確認へ自動降格。
  更新3経路:マージ時/前提崩壊時/網羅的調査時。内容は事実のみ=人間ゲート不要
- モデル割当:曖昧さの判断=Fable 5/決まったことの実行=Opus 5/機械的照合=Sonnet 5。
  ただし静的な設計でなく、evalのモデル別実行で実績更新する運用パラメータ
- 補正系の指示(言い訳潰し・手順の強制)はモデル欠陥の写し。世代交代時に
  ablationで剪定する前提でマークしておく。ドメイン知識と補正を混ぜない
- NG調査は証拠連鎖の逆向き二分探索:期待に書かれていたか→実現案に反映されたか→
  実装が乖離したか→テストが検出できたか。帰属先にトリアージ誤判定を含む

## 初期実装(試走の装備)と仮説リスト

作るのは3点のみ:期待テンプレート+clarify-expectation+verify-traceability。
他は素のClaude Code+本文書への都度指示で一周し、痛みを観測してからスキル化。
既存スキルの流用可否(diagram-design、webapp-testing、interview-me等)は
エンジンとして評価し、契約(本文書の規律)は自作を維持する。

試走の観測項目:解明の往復回数/各ゲートの承認時間と読み味/前提崩壊の有無/
QA NGの有無/フェーズ別コンテキスト消費。これが最初のeval素材。

仮説リスト(設計に足さず試走で検証する):Sの軽量経路の書式/clarify・decomposeの
統合か分離か/⚠予算の適正数/マップの鮮度閾値/コンテキスト契約の中身/
本番シグナルのNG調査還流。
