# GitHub Issue 解決フロー — 設計思想

スキル(SKILL.md 等)を書くときに参照する思想文書。スキルはこの思想の一表現で、モデル世代・コードベース・試走の観測に合わせて書き直す。この文書も同じで、今のフローを良くする形に常に更新する。過去の版は git にある。

図解版は `github_issue_flow.html`。本文書はその文章版で、両者は同じ設計を指す。

## 核

- GitHub は具体(Issue に記載された確定した要件、PR マージによる解決の事実)、Slack は抽象(報告・要望・検討のコミュニケーション)。抽象→具体の翻訳だけが本質的に人間の判断を要する
- 方針: 開発者の労力を最小に、最大の品質を。労力には**将来の労力**を含む — AI の判断を人間が判断できなくなる事態が最大のコスト
- 承認は労力ではなく、**理解を生産する投資**。高速化した開発に対して理解の速度を上げつつ品質を保つ仕組みである
- 人間は散文を読まない。承認の対象は表と格子で出す。散文は読み下しと背景だけ

## 3つのゲートと検証の分担

人間が理解するのは3点だけ:

| ゲート | 担保するもの | 読むもの |
|---|---|---|
| ① 要件の承認 | 問題を正しく捉えたか | 完了基準(C)と受け入れ基準(T)の表、状態×操作の格子、要件確認コメント(別コメント)、懸念、変更履歴 |
| ② 実現案の承認 | 進み方は妥当か(承認=仮説の採択。実装は反証実験) | T ごとの対応可否の目次表、変更がある機能単位の節、設計判断の根拠・⚠懸念点(却下案は折りたたみ) |
| ③ フィードバック | 要件がテストに正しく翻訳されたか | T→テスト対応表とテストコード(実装ではない) |

実装そのものはどのゲートも読まない:

- 実装の**正しさ** → E2E の観測が担保(AI の誠実さと無関係に真)
- 実装の**健全性** → 前提崩壊率(内部の腐敗の遅行指標)
- 性善説(想定と違えば NG を出すはず=承認をもって理解とみなす)は**承認の判断にのみ**適用する。信用が必要な面積を最小化し、残りに性善説を適用する

## 定常フローの骨格

4つのレイヤに分け、スキル名の先頭にレイヤとレイヤ内の順序を付ける。要件→設計→検証が Issue ごとの定常フロー、資産化(improve)は試走のあとに回るメタループ。

| レイヤ | 順 | スキル | 産物 |
|---|---|---|---|
| 要件 | 1 | req-1-triage-issue | S/M/L 判定・根拠一行・完了基準 C1〜Cn |
| 要件 | 2 | req-2-survey-codebase(L のみ) | 入口・経路の前提確認・C ごとの3問表・前例・マトリクス・Issue 未記載の関わり・影響マップ・system-map |
| 要件 | 3 | req-3-clarify-expectation | 実装前の要件・受け入れ基準の整理(格子・T 表)と、別コメントの要件確認 → ゲート① |
| 設計 | 1 | design-1-propose-with-diagram | 実現案(目次表・機能単位・図は任意・根拠と⚠懸念点の 2 段・却下案と実装メモは折りたたみ)→ ゲート② |
| 実装 | — | 自作スキルなし | 前提崩壊の申告プロトコルのみ |
| 検証 | 1 | verify-1-traceability | T→テスト対応表・未カバー・エスカレーション → ゲート③ |
| 資産化 | 1 | improve-1-distill-feedback | 試走の指摘 → 台帳の行(固有語なし)→ 改善 Issue draft → マージ後の状態更新 |

QA での NG は NG 調査へ還流(未実装。痛みを観測してから)。

## 背骨: 完了基準(C)と受け入れ基準(T)

- C は req-1 が Issue の語のまま採番し、req-2 は C ごとに「既存で満たせるか / 新規の仕組みが要るか / repo 外依存」を答え、req-3 は C と T の対応表を置く
- T は req-3 が E2E で観測できる Given/When/Then として採番する。design-1 の目次表、子 Issue の本文、verify-1 の照合はすべて T の ID で参照し、工程を跨いで振り直さない(投稿前なら欠番を詰めてよい。ID 固定は投稿後から)。Given の状態を現環境で作れない振る舞いは T にせず、C を「対応なし(理由)」にして制約へ
- 散文の Asis/Tobe は読まれない。T 表と、その概観としての状態×操作の格子を初版から出す

## 要件レイヤの規律

- **トリアージ S/M/L**: 根拠を一行記録(ゲート①で人間の目に入る)。迷ったら上に倒す。S は工程を畳むが承認は省かない。L は領域×観点マトリクス(FE/BE/IaC/データ × 参照/変更/暗黙の依存)の全セル消込が分割の前提条件
- **網羅的調査の2層**: 上層=C ごとの3問表(人間が読む)、下層=影響マップ(AI が読む)。調査の前に入口ごとの経路の仮定を 1 問ずつ確認し、「分からない」入口だけ横断調査する。ドメイン語を全領域で横断探索し、どの C にも対応しない出現箇所と、データの流れ(入口→保存→表示面)上の表示面を「Issue 未記載の関わり」として要件確認候補に出す。同種の新規成果物の直近の前例を1件挙げる。確信度の語は「直接/経由/関係しうる」(重要度と誤読させない)
- **格子で見落としを潰す**: Given×When の格子に既存操作(取消・一括処理・権限の無い利用者)を既定で並べ、「ルールが効かない側」のセルを1つずつ確認する。埋まらないセルが要件確認の候補。隣接機能の行は、経路・データ・処理を共有する根拠(パス:行)があるときだけ(回帰の担保はテストの責務)。同じ T を入れた複数セルは、出力前に Then が本当に同じかを既存コードで確認する(自己精査)
- **質問の3分類ルーティング**: 人間に届くのはビジネス判断だけ。技術判断は調査で自己解決(根拠をコンテキストへ記録)、些末はデフォルト案+通知。ビジネスか些末かで迷ったときだけ聞く側に倒す。要件確認は本文と別のコメントで、`ID / 概要(体言止め) / 質問(敬体の問い 1 文)` の 1 表。本文の該当箇所は「※要確認」だけ。Issue の要件を置き換える提案は求められたときだけ
- **技術事実は囲みを読んでから断定する**: grep の一致行だけで「設定の内側」と書かない。ゲート・フラグ・権限の主張は確信を1段下げ、根拠行(パス:行+原文)を要約で落とさない
- **受け入れ基準は E2E で観測可能な語彙のみ**。観測不能な行は書き直すかコンテキストへ。実装語彙(クラス名・ライブラリ名)が漏れたら分離の失敗
- **最大分割**: 基準は「独立に検証可能な最小の受け入れ基準の単位」かつ「単体で既定ブランチにマージできる単位」。実装の都合や数の多さは基準にしない。切れない結合は**統合期待**として親 Issue に残す。親の本文では子 Issue を「子1〜子n」と呼び、番号は完了基準の表の「子 Issue」列に 1 回だけ `#` なしで書く(`#番号` は編集のたびに参照先の timeline が反応する)。T→子 Issue の対応は子 Issue 本文が持つ
- **変更履歴**: 投稿した版からの差分だけ。投稿前の往復は「初版」1 行。どの回答(コメント URL)・調査結果を受けて、どの行が変わったか。3列で details に入れる。承認は全文でなく差分のレビュー。実装からの差し戻し(前提崩壊)もここに追記

## Issue の構成

本文は「人が承認するもの」だけ。問いと回答、AI の懸念、AI が参照するもの、履歴は本文から分ける。

| 部分 | 中身 | 読み手 | 形 |
|---|---|---|---|
| **実装前の要件・受け入れ基準の整理**(承認対象) | トリアージ・業務背景・完了基準(子 Issue 列と先行関係)・格子・受け入れ基準の表・影響画面・制約・統合期待 | 起票者は格子まで、T 表は実装者と verify-1 向け | 本文。各節の見出し直下に関係を示す引用ブロック 1〜2 文(「読み方: C → 格子 → T → 要件確認」)。要件確認が要る箇所は「※要確認」だけ。非機能の節は置かない(T や制約に無い要求だけ制約に 1 行) |
| **要件確認** | ビジネス判断の問い。`ID / 概要 / 質問` の 1 表 | 起票者 | **別コメント**。本文の投稿指示とは別に「要件確認を投稿」の指示があるまで出さない。回答を受けた更新は変更履歴に回答コメントの URL |
| **懸念** | AI の懸念。件数上限なし。各項目はチェックボックス+⚠n 見出し+説明+「解決:」欄+補助表 | 承認者(妥当性を判断してコメントで返す) | 文末の大見出し `## 懸念`、`<details>`(summary に件数と未解決数) |
| **コンテキスト(エージェント参照用)** | 出典・調査結果・技術判断の根拠・些末判断 | エージェント(人間は原則読まない) | 文末の大見出し、`<details>`。長命 — 参照の連鎖で辿れること |
| **変更履歴** | 投稿した版からの差分 | 承認者(差分のレビュー) | 文末の大見出し、`<details>` |

文末の順は 懸念 → コンテキスト → 変更履歴。短命 — マージでクローズ。記録として書き、呼びかけ文やフロー用語(「ゲート①」「期待」)は書かない。本文に `#番号` を書かない。

## 実現案の提示仕様(違和感の検出器として設計する)

1. 目次表が先: T ごとに「対応可否 / 対応内容 / 機能単位」。対応可否は「あり」「なし(Tn で達成)」の短い語だけで、変更なしの理由はここに集約する。直後に「実装が要るのは Tn だけ」を1行置く
2. 機能単位(画面/クエリ/バッチ/マスタ等)の節は、変更がある機能だけ。利用者の語で書く
3. 図は任意: 機能単位が3つ以上か依存があるときだけ描き、描かないなら「省略」と明記する。描くなら変更タイプ別の型(画面→Before/After 状態遷移、API→シーケンス+スキーマ差分、IaC→構成図差分、データ→流れの Before/After)
4. `### 設計判断の根拠・⚠懸念点` の下に `#### 設計判断の根拠` / `#### ⚠懸念点` の 2 段。各項目は太字見出し 1 行(結論)+ネストした説明(1 文 1 項目)。⚠懸念点は `**⚠1. 見出し**` で採番し、「案が成り立たなくなる条件」と「利用者・運用に見える副作用」だけ(開発者の通常確認事項・未リリース機能への影響・既存機能の性質上避けられない挙動は書かない)。件数上限なし。読み手が辿れない前例(他 Issue・他 repo・別契約者)は根拠に書かない。候補を2つ以上立て、**却下案+却下理由**は `<details>` に折りたたんで実装メモの前に置く
5. `<details>実装メモ(AI 用)</details>` を必須で置く: 触るファイルと順序・インターフェース契約・検証コマンド。人間向けの本文と混ぜない
6. 差し替えのたびに `<details>修正履歴</details>` に1行足す
7. 実現案はその Issue で完結させ「何をしなければならないか」だけ書く。他の子 Issue・親 Issue・要件確認への言及(依存・共有・凍結)を書かず、決まった事実はその Issue の語で直接書く。データ構造は本文では方針の粒度(何をどの形で持つか・未設定・既存データの扱い)、列名・型は実装メモ
8. 人間向け本文で言い換えるのは、コードを読まないと分からない語(クラス名・関数名・設定キー)だけ。チームで共有されている技術語(ライブラリ名・基盤名)はそのまま使う

## 実装フェーズ

- 実装は純粋な実行ではなく**最後の調査フェーズを兼ねる**
- 前提崩壊の申告は正常な出力: 「前提 X が崩れた。現地はこうだ」と申告して停止。回避策を積んで実現案を守り抜かない(隠すコストが最も高い)
- 差し戻し3方向: 実現案の誤り→②へ(却下理由を資産化)/ 要件の前提の誤り→①へ(変更履歴に追記)/ 負債が障害物→実行時分割(負債解消単位+依存する機能単位)
- PR は単体で既定ブランチにマージできる単位。積み上げ PR は CI・rebase・生成物更新が段の数だけ発生するので作らない

## 品質担保

- T→テスト対応表+エビデンス: 受け入れ基準の全行が E2E で覆われることの機械的証明。T の ID をそのまま使う
- ゲート③は2モード: **育成**(テストコードを厳格に。指摘は資産へ変換)→ **巡航**(対応表のみ。移行条件: ⚠外指摘率の低下。移行を急がないことが性善説の担保)
- 実装図解と実現案図の機械突合、system-map diff の生成は未実装。図が任意になったため、必要になったら設計し直す

## 通底する原則

- 指摘はインスタンス(その Issue)でなく資産(SKILL.md・assets・principles・CLAUDE.md・map)に還元する。人間は diff の承認のみ。変換は improve-1-distill-feedback が担う: 観測 → 台帳の行 → 改善 Issue draft → PR(文面はここで)→ マージ後に台帳の状態を「反映済(版)」へ。台帳と draft は対象プロダクトの固有語を含めない(公開 repo の Issue に転記できる形)
- 出力先は作業用のメモ置き場。repo・GitHub への書き込みは明示指示があるときだけ。投稿は単位ごと(本文・要件確認コメント・起票)に指示を取る(`references/principles.md`)
- コンテキストは渡さず取りに行かせる。フェーズ別に入力契約(読んでよいもの/いけないもの)を宣言。フェーズ間は成果物のみ受け渡し、会話履歴を持ち越さない。突合役に判断の物語を読ませない
- system-map は**索引であって本文ではない**(場所・関係・鮮度のポインタ集。要約の転記禁止)。鮮度メタデータ必須、古い項目は未確認へ降格
- モデル割当: スキルの実行はすべて **Opus 5.5**(SKILL.md の `model:` で指定)。判定役(eval の採点、verify-1 からのエスカレーション先、ゲートで人間を補助する読み手)は **Fable 5.1**。静的な設計でなく、eval を実際に使うモデルで回して更新する運用パラメータ
- 補正系の指示(言い訳潰し・手順の強制)はモデル欠陥の写し。世代交代時に ablation で剪定する前提でマークしておく。ドメイン知識と補正を混ぜない
- NG 調査は証拠連鎖の逆向き二分探索: 要件に書かれていたか→実現案に反映されたか→実装が乖離したか→テストが検出できたか。帰属先にトリアージ誤判定を含む
