GitHub Issue解決フロー v3凍結版・北極星

方針：開発者の労力を最小に（将来の労力を含む通時的最小化）、最大の品質を。承認は労力ではなく理解を生産する投資。GitHub＝具体、Slack＝抽象。以後の改善は本設計への追加ではなく、試走で検証する仮説として扱う。

人間が理解するのはこの3点だけ

  • 期待の正しさ（ゲート①）— 問題を正しく捉えたか
  • 判断の方向（ゲート②）— 進み方は妥当か（承認＝仮説の採択。実装は反証実験）
  • 翻訳の一致（ゲート③）— 期待がテストに正しく落ちたか

実装は人間が読まない。代わりに観測と指標が担保する

  • 実装の正しさ → E2Eの観測（AIの誠実さと無関係に真）
  • 実装の健全性 → 前提崩壊率（内部の腐敗の遅行指標）
  • 性善説は「承認の判断」にのみ適用。信用が必要な面積を最小化して残りに適用する
AIが実行 人間ゲート 例外・差し戻し 資産・メタループ 世代交代 コンテキスト規律
トリアージS / M / L 判定＋根拠を一行記録（ゲート①で人間の目に入る）
  • S：軽量経路（解明と実現案を1コメントに畳む。承認は省かない — 理解コストが小さいから速いだけ）
  • M:標準経路（下記フルフロー）
  • L:網羅的調査を前置してからフルフロー
誤判定はNG調査の帰属先の一つ（L相当をMと誤ると調査不足のまま分割し多単位で崩壊する）
網羅的調査Lのみ・最大分割の前提条件
  • 領域×観点マトリクス（FE/BE/IaC/データ × 参照/変更/暗黙の依存）の全セルを「確認済み/未確認」で埋める — 網羅の定義を先に固定し自己申告を検証可能にする
  • システムマップを起点に差分確認（全量探索は初回のみ。以降は地図の更新）。並列サブエージェントで領域ごとに探索し集約
  • 未確認セルは⚠として期待側に浮上し、ゲート①で人間の目に入る
産物：影響マップ（確信度つき）→ システムマップへ還元（探索系更新）
解明フェーズ曖昧さの解消＋問題の最大分割
  • 期待の詳細化 ⇄ 現状調査（改修/新規、FE・BE・IaC領域判定）
  • 質問ルーター：ビジネス判断→人間／技術判断→調査で自己解決／些末→デフォルト案＋通知
  • 最大分割：独立に検証可能な最小の期待単位へ。依存グラフ作成。単位を跨ぐ期待は「統合期待」として親Issueに残す
  • 期待の変更履歴：どの調査結果を受けて、どの行が、なぜ変わったか（実装からの還流も受ける）
産物：単位ごとの期待文書（Asis/Tobe・影響画面・制約。実装語彙を含まない）＋変更履歴＋依存グラフ＋背景コンテキスト
ゲート① 期待＋変更履歴＋分割の承認 — 提示は差分中心：L1＝単位一覧と依存図＋初版から変わった行のハイライト、L2＝変更理由と分割根拠。人間は「なぜこの形に変わったか」の妥当性だけ判断
分配ポイントA（垂直・原則）：承認済みの期待単位ごとに担当（人間/エージェント）へ配り、以降のパイプラインを丸ごと持たせる。契約が凍結された地点でのみ安全に並列化できる — 解明フェーズ自体は分配不能（曖昧なまま配ると解釈が人数分に複製される）
実現案 単位ごと
  • 実現案の作成（背景コンテキスト＋依存グラフ＋マップを判断材料に）
提示仕様（違和感の検出器として設計する）
  1. 期待の語彙で書く — 振る舞いの因果が主表現。実装語彙はL3へ
  2. 三層：L1＝図1枚（ここだけでNG判断が成立）／L2＝判断根拠と却下案＋却下理由／L3＝実装計画（人間は原則見ない）
  3. ⚠の名指し（予算：最大3）— リスク・低確信・解釈が入った箇所をAI自身が宣言
  4. 図形式は変更タイプ別に固定（画面→Before/After状態遷移、API→シーケンス＋スキーマ差分、IaC→構成図差分）— 読み慣れで承認が速くなる
  5. 「分かりにくい」の指摘は提示形式へ還元（メタループ対象）
ゲート② 実現案の承認 ＝ 現在の知識で最善という仮説の採択。実装はその反証実験。差し戻しは失敗ではなく想定内動作
分配ポイントB（水平・単位が大きすぎる時のみ）：実現案が定義したインターフェース契約（APIスキーマ等）に沿って実装だけを分ける。契約凍結前の水平分割は禁止
実装 単位ごと
  • 承認済み実現案に沿って実行（Opus 5）。実装は純粋な実行ではなく最後の調査フェーズを兼ねる
  • 前提崩壊の申告プロトコル：「前提Xが崩れた。現地はこうだ」と申告して停止することを正常な出力として定義。回避策を積んで実現案を守り抜かない（隠すコストが最も高い）
3方向差し戻し（崩れたものの種類で分岐）
  • 実現案の選択が誤り → ゲート②へ。却下理由を背景に追記（同じ袋小路に二度入らない）
  • 期待の前提が誤り → ゲート①へ。変更履歴に「実装時の発見により改訂」
  • 負債が独立した障害物 → 実行時分割：負債解消単位＋機能単位（依存）に切り、それぞれ通常フローへ
前提崩壊はマップの該当項目を同時修正（例外系更新）。崩壊率は領域別に集計 → コードベースの健康診断指標・負債返済Issueの起票根拠
品質担保 単位ごと＋統合
  • 実装内容の図解（実現案と同形式）→ 実現案図と機械突合。「図解しか見ない」運用の前提を機械が担保
  • E2Eテスト：期待の各行→観測可能な振る舞いへ翻訳。統合期待は親Issue側で検証
  • 期待→テスト対応表＋エビデンス（スクリーンショット・実行ログ）— 全行カバーの機械的証明
  • システムマップdiffを生成（正常系更新。マージに同梱）
ゲート③ フィードバック（2モード） — 人間が読むコードは実装ではなくテストコード（期待と同じ語彙で書かれ、AIの解釈が最も裸で現れる場所）
育成モード（初期）図解＋テストコードを厳格にチェック。「このケースはダメ」「この実装だと〜が起きる」を具体的に出す → 資産へ変換。⚠に挙がっていなかった指摘の率を計測（検出漏れの実測） 巡航モード（成熟後）図解のみ。移行条件：⚠外指摘率が十分低下＋図解⇔実装突合の機械化が安定。移行を急がないことが性善説の担保
PRマージ 小さなPRの束
  • コードとマップdiffが同一コミットで整合。期待文書はクローズ（短命）、背景・決定・evalは資産へ（長命）
  • QAフェーズ（後続）のNGはNG調査へフィードバック

例外フロー：NG調査

承認済み成果物を境界に証拠連鎖を逆向きに二分探索。分割済みのため爆風半径は1単位。

期待に書かれていない→ 解明の欠陥。人間の再承認イベント
実現案・実装が乖離→ 差し戻しリトライ。期待は不変
テストが未検出→ テスト観点の漏れ
トリアージの誤判定→ 判定基準の改訂
プロセスの誤り→ 資産改訂（宛先つきdiff提案）

資産（沈殿先）

evalセット永続資産の本体。実運用Issueが素材。SKILL.mdより長生きする仕様
システムマップ索引であって本文ではない（場所・関係・鮮度のポインタ集。要約の転記禁止）。鮮度メタデータ必須：最終確認Issue＋日付、古い項目は「未確認」へ自動降格。更新3経路＝マージ時（正常系）／前提崩壊時（例外系）／網羅的調査時（探索系）。内容は事実のみ＝人間ゲート不要、スキーマ変更のみ資産diffとして承認
期待テンプレート／SKILL.md群世代ごとに書き直し可能な実装
CLAUDE.md・コンテキスト文書コードから読めない恒久知識
決定ログ仕分け結果・フェーズ別NG混入率・前提崩壊率の集計元

コンテキスト最小化（実行時の規律）

コンテキストは渡さず、取りに行かせる。マップはその索引。

フェーズ別入力契約各SKILL.md冒頭に「読んでよいもの」全列挙＋「読んではいけないもの」明記。例：突合役に実現案の判断理由を読ませない（採点が甘くなる）— 最小化は独立性の注入でもある
フェーズ間は成果物のみ会話履歴を持ち越さない。往復は期待文書と変更履歴に蒸留された時点で役目を終える
予算の計測フェーズ別トークン・読了ファイル数を試走から記録。契約外読込は契約かマップの欠陥としてメタループへ

世代交代ループ（skill-gardener）

モデル更新を検知したらスキルを剪定する。ドメイン知識は残し、旧モデルの欠陥補正だけを削る。

1. 新モデルでeval再実行使用頻度・NG混入率の高い順
2. Ablation指示ブロック単位で抜いて再eval。抜いても落ちない＝削除候補
3. 新モデル特有の失敗へ補正提案
4. diff提案→人間承認gardener自身の改訂は人間レビューを厚く（自己言及禁止）
メタループ（当面は週次の手動棚卸し）：解明の訂正履歴（事前の予防接種）＋育成モードの具体的指摘＋QA NG＋NG混入率＋前提崩壊率＋コンテキスト予算が、資産diffへ沈殿。フェーズ別混入率が投資判断と育成→巡航移行の根拠。世代交代ループが資産をモデル更新のたびに剪定し、evalセットだけが世代を越えて生き残る。

スキルとモデル割当

原則：曖昧さ・トレードオフの判断＝Fable 5／決まったことを決まった通りに＝Opus 5／機械的照合・翻訳＝Sonnet 5。evalは常に実際に使うモデルで実行。初期実装＝試走で最初に作る3点。残りは素のClaude Codeへの都度指示で代替し、痛みが観測されてからスキル化。
スキル担当モデル割当理由
clarify-expectation初期実装 詳細化・質問ルーター・変更履歴・E2E可能語彙のプリフライト（＋当面decompose-issueを内包） Fable 5 曖昧さの検出がフロー全体の品質上限。「各行はE2Eで観測可能か」の検査を含む
decompose-issue 最大分割・依存グラフ・統合期待。実行時モード（負債の切り出し）を含む Fable 5 「独立に検証可能な最小単位」の切り出しは設計判断。肥大したらclarifyから分離
survey-codebase 網羅的調査（L経路）・マトリクス消込・マップ拡充 Opus 5 網羅的探索の正確性勝負。領域別に並列サブエージェント→集約
investigate-codebase 単位ごとの現状調査・領域判定 Opus 5 定型手順の正確な探索。判断より網羅
propose-with-diagram 実現案＋提示仕様準拠の図解（三層・⚠・却下案・形式固定） Fable 5 トレードオフの選択と違和感検出器の生成。レンダリングはスクリプトへ
（実装） 自作スキルなし。既存の型＋前提崩壊申告プロトコル Opus 5 決まったことを決まった通りに。Fable不要（方針どおり）
verify-traceability初期実装 図解突合・期待→テスト対応表・エビデンス・マップdiff生成 Sonnet 5 照合と翻訳。高頻度なのでコスト効率優先。迷う差分のみ上位へエスカレーション。人間の理解の入力の忠実性を担保する土台
（期待テンプレート）初期実装 Issueの「期待」（人間承認）／「コンテキスト」（承認不要）の2部構成＋非機能の定型欄 — スキルではなく.github/ISSUE_TEMPLATE。全工程の正解の定義
attribute-defect NG調査・帰属・改訂diff提案 Fable 5 因果推論と抽象化。低頻度・高価値
distill-feedback ゲート③指摘の資産diff化（当面は手動棚卸し） Fable 5 個別→一般則の昇華。育成→巡航遷移の心臓部
skill-gardener モデル更新検知・eval再実行・ablation剪定 Fable 5 剪定判断はFable、eval実行は移行先の各モデルで

初期実装（試走の装備）

  • 期待テンプレート＋clarify-expectation＋verify-traceability の3点のみ
  • 他フェーズは素のClaude Code＋本設計文書への都度指示で一周する
  • 試走の観測項目：解明の往復回数／各ゲートの承認時間と読み味／前提崩壊の有無／QA NGの有無／フェーズ別コンテキスト消費 — これが最初のeval素材
  • 独立レビューを1箇所：マージ前に期待文書と実装だけを渡した別コンテキストのレビュー（実現案・対応表を見せない）— 自己採点の相関を切る最安の手段

仮説リスト（設計に足さず、試走で検証する）

  • Sの軽量経路の具体形（1コメント畳み込みの書式）
  • clarify / decompose の統合維持か分離か
  • ⚠予算の適正数（3で足りるか）
  • マップの鮮度閾値（何日/何Issueで未確認へ降格するか)
  • コンテキスト契約の中身（実現案に変更履歴を見せるか等）
  • 本番シグナル（障害・報告）のNG調査への還流 — QAすり抜け率が問題になってから
